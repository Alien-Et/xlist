# Self-Check & Repair（自检自修闭环）

一套可复用的"自检 → 修复 → 验证 → 推送 → 报告更新"流程，源自 xlist（Flutter WebDAV 文件管理器）的持续迭代实践，可迁移到任何代码项目。

## 适用场景

- 用户要求"自检/自查/全面检查项目"并修复发现的问题
- 用户连续报告一批 bug，需要系统化定位根因并修复
- 用户明确要求"每修一个问题都要和所有脚本比对耦合度"
- 需要维持长期可维护性（死代码、矛盾、重复逻辑治理）

## 核心原则

1. **探查优先**：动手前完整读取相关代码与报错，不凭印象猜测；连续两次读取不再改变计划即开工。
2. **守住边界**：只改用户点名的范围；建议性改动先交互确认；保留未要求改动的逻辑与原始状态词。
3. **证据驱动**：每个根因必须有代码证据（grep 调用方/读实现）；结论区分"已查证"与"推测"。
4. **耦合比对**：**每修一个问题，必须 grep 该符号/文件的所有引用方**，确认修复不破坏其它调用点；新出现的不一致要么修掉要么记录。
5. **验证门禁**：静态检查 0 error 是底线；运行测试/构建/真实入口；产物用不同于生成路径的方式回读。
6. **报告同步**：项目若维护架构报告（如 PROJECT_MAP.md），每次修复后必须更新"死代码清单/矛盾清单/变更记录"。

## 流程

### 阶段一：探查与分类

1. 收集输入：用户报的 bug 清单、截图、报错日志、可复现步骤。
2. 建立任务清单（task_create），每个 bug / 自检项一个任务。
3. 对每个 bug 定位代码位置：
   - `grep -rn "<关键字>" <源码目录> --include="*.<ext>"` 找引用方
   - 读目标文件确认实现细节（根因必须在代码里找到证据，禁止臆测）
4. 根因分类：
   - **逻辑错误**（判断/分支/返回值错误）
   - **耦合断裂**（服务未注册、参数不匹配、调用方未同步）
   - **死代码**（无调用方的方法/字段/分支）
   - **功能矛盾**（两套实现并存、接口语义不一致）
   - **资源风险**（并发无上限、缓存不失效、内存/连接爆）

### 阶段二：修复（按根因分策略）

| 根因类型 | 修复策略 |
|---|---|
| 逻辑错误 | 只改错误逻辑本身，不重写整体；修复后核对相邻逻辑 |
| 耦合断裂 | 补齐注册/参数/调用方；用 try-catch 对易碎点做容错；错误文案要指向真实原因，不误导 |
| 死代码 | 先 grep 确认零引用，再删除（含相关导出/import）；为 API 预留的标注保留理由 |
| 功能矛盾 | 统一到单一实现；删除旧实现或标记"待收敛"，不得静默替换 |
| 资源风险 | 加并发上限/分批/缓存版本号/超时；优先简单可靠的无依赖方案 |

### 阶段三：耦合比对（每次修复后必做）

```
# 对每个改动的符号/文件：
grep -rn "<被改符号>" <源码目录> --include="*.<ext>"
# 检查：
# 1. 所有调用方是否仍兼容（参数/返回值/异常路径）
# 2. 是否有其它文件引用了被删除的死代码
# 3. 新引入的 import / 依赖是否被正确声明
# 4. 同一模式是否有复制粘贴的未改副本（如多个页面同款逻辑）
```

### 阶段四：验证

1. 静态检查：`<analyzer> analyze` 必须 0 error（存量 warning 记录数量与位置，不在本轮扩大）。
2. 构建/测试：按项目技术栈执行（如 `flutter build apk --debug`、`npm run build`、`pytest`）。
3. 回读：用与生成不同的方式检查产物（文件存在≠正确；抽查关键数据/界面）。
4. 未验证项如实披露，不悄悄降级。

### 阶段五：推送与报告

1. 提交信息按批次归类：`fix: <批次> - <问题1>/<问题2>...`，便于回溯。
2. 推送远程（用仓库既有凭据机制，命令不含敏感 token）。
3. 更新架构报告（若存在）：
   - 死代码清单：新增项 + 状态
   - 矛盾清单：新增项 + 状态
   - 变更记录：日期 / commit / 变更摘要
4. 交付物（APK/构建产物/报告）用 present_files 交付；说明验证方式、覆盖范围、剩余缺口。

## 检查清单（可复用模板）

- [ ] 每个 bug 都有代码证据定位的根因
- [ ] 每次修复后 grep 比对全部调用方
- [ ] 死代码删除前确认零引用
- [ ] 矛盾统一到单一实现或明确记录
- [ ] 并发/递归有上限保护
- [ ] 缓存/列表 key 含数据版本维度
- [ ] 服务/依赖注册完整（Get.put / DI 容器 / 依赖注入）
- [ ] 错误文案指向真实原因
- [ ] analyze 0 error、构建成功、产物回读通过
- [ ] 报告文档已更新（死代码/矛盾/变更记录）
- [ ] 推送成功且 CI 状态确认

## 维护规则

- 本 Skill 本身也应随实践迭代：流程中发现新的坑（如"无并发上限导致闪退"），把经验补进对应小节。
- 报告文档的"修复守则"与本 Skill 保持一致，二者同步更新。
